   весь JavaFX-код (`HashTableView`, контроллер, задачи, FXML), `JsonBatchSerializer` и JUnit-тесты.
   Код написан аккуратно, но первый запуск у тебя — это и есть проверка. Если что-то красное — присылай текст ошибки.

Как соответствует требованиям минимума: структура с вставкой/поиском/удалением; полная перерисовка панели после
каждой операции (`refresh(...)` в контроллере); генерация набора данных с числом записей; фоновая загрузка файла через `Task` с прогрессом.

**Если хочешь прикручивать сама**, самое важное в контроллере:
- `service.findAll()` теперь `Batch[]` — `rows.setAll(...)` принимает массив без изменений;
- вместо `refresh()` — `refresh("описание операции")`: он и таблицу обновляет, и вызывает `hashView.render(...)`;
- фоновая задача: `new Thread(task).start()`, результат берётся в `task.setOnSucceeded(...)`, а в структуру
  данные кладутся **в потоке JavaFX** — так фоновый поток и интерфейс никогда не трогают таблицу одновременно.

### Таблица асимптотики для отчёта (n — число элементов, m — ёмкость, α = n/m ≤ 0.75)

| Операция | В среднем | В худшем | Обоснование |
|---|---|---|---|
| put / putIfAbsent | O(1) | O(n) | при α ≤ 0.75 в среднем ≈ 2.5 пробы (успешный поиск) и ≈ 8.5 (неуспешный): ½(1+1/(1−α)) и ½(1+1/(1−α)²); в худшем все ключи в одном кластере |
| get / containsKey | O(1) | O(n) | то же |
| remove | O(1) | O(n) | поиск + пометка DELETED |
| рехеш | O(m) | O(m) | все живые элементы вставляются заново; амортизированно на одну вставку O(1), т.к. ёмкость удваивается |
| findAll / forEach | O(m) | O(m) | обход всех ячеек |
| clear | O(m) | O(m) | выделение новых массивов |

Для выводов: на подряд идущих ключах (1, 2, 3, …) линейное пробирование даёт длинные кластеры, и
неуспешный поиск сканирует весь кластер; у сгенерированных (разбросанных) артикулов в моём прогоне на 100 000 записей
было около 3.6 пробы на операцию. Цифры ориентировочные — сними свои на `FormatBenchmark`-подобном замере.
